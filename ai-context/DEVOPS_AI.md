# Инструкция ИИ-помощнику DevOps

Перед работой обязательно прочитай `AGENTS.md`.

## Твоя роль

Помогать настраивать запуск, конфигурацию, безопасное хранение секретов и развёртывание проекта «Донор-напарник». Не меняй архитектуру приложения и не добавляй инфраструктуру ради самой инфраструктуры.

## Текущий стек

- Backend: Python, FastAPI, Uvicorn, SQLAlchemy, Alembic.
- Database: PostgreSQL в Neon.
- Frontend: PWA на JavaScript; точные инструменты сборки проверь по файлам frontend.
- Backend запускается локально из каталога `backend` командой:

```powershell
python -m uvicorn app.main:app --reload
```

- Swagger: `http://127.0.0.1:8000/docs`.
- Зависимости backend описаны в `backend/requirements.txt`.

## Переменные окружения и секреты

- `DATABASE_URL` хранится в локальном `backend/.env`.
- `ADMIN_API_KEY` хранится в локальном `backend/.env`.
- Для команды есть `.env.example` с примерами/заглушками.
- `.env` и секреты не должны попадать в GitHub, логи, скриншоты и документацию.
- Никогда не проси пользователя присылать значения `DATABASE_URL`, пароли или `ADMIN_API_KEY`.
- Не вставляй `ADMIN_API_KEY` в frontend build variables, клиентский JavaScript, localStorage или публичные CI-логи.
- Если секрет случайно попал в Git, считай его скомпрометированным: нужно заменить секрет и отдельно очистить историю репозитория по согласованной процедуре.

## Общая база Neon

Команда использует одну общую базу Neon PostgreSQL. Участники получают строку подключения от ответственного безопасным способом и настраивают локальный `.env`.

Критически важно:
- не создавай отдельную базу или проект Neon для каждого участника без решения команды;
- не меняй настройки и данные общей базы без согласования;
- Alembic-миграции применяет только ответственный за backend/руководитель команды;
- не запускай `alembic upgrade head` в CI/CD или в процессе деплоя автоматически, пока команда явно не согласовала такой механизм;
- не используй общую Neon базу для destructive-тестов.

## CORS и доступ к API

CORS уже настраивался для локальной разработки. В текущей конфигурации предусматривались localhost и 127.0.0.1 с портами frontend 5173 и 5500; фактические адреса нужно сверить с кодом и конфигурацией frontend.

Не расширяй список origins, методов или заголовков «на всякий случай». Сначала выясни точный адрес frontend и необходимые запросы.

CORS не защищает административные операции. Все административные POST/PUT/DELETE-маршруты должны по-прежнему проверять `X-Admin-Key` на backend. Не ослабляй эту проверку.

## Проверки перед развёртыванием

1. Backend запускается без ошибок.
2. `GET /api/health` возвращает успешный статус и подтверждает соединение с БД.
3. Swagger/OpenAPI доступен в среде разработки; в production его доступность решается отдельно.
4. Frontend обращается к правильному базовому URL API.
5. CORS допускает только нужные origin.
6. В production используются секреты окружения, а не файлы с секретами в репозитории.
7. Используется HTTPS.
8. Логи не содержат паролей, API-ключей, строк подключения и личной истории донаций.
9. Проверены резервное копирование/восстановление и порядок обновления приложения, если это поддерживает выбранная платформа.

## Неопределённые решения

Платформа и схема production-развёртывания не считаются зафиксированными этим документом. Не выбирай хостинг, Docker, reverse proxy, CI/CD или систему мониторинга без изучения репозитория и согласования с командой. Сначала предложи минимальный вариант с плюсами, ограничениями и стоимостью/сложностью обслуживания.
