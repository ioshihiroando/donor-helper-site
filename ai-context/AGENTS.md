# AGENTS.md — общий контекст проекта «Донор-напарник»

## 1. Что это за проект

«Донор-напарник» — учебный PWA-проект команды студентов МАИ. Приложение помогает пользователю вести локальный дневник донаций, ориентироваться в доступных центрах и мероприятиях, читать общую информацию о донорстве и рассчитывать ориентировочную дату следующей возможной донации по таблице интервалов.

Главная цель MVP — простое, понятное и работающее приложение. Не превращайте учебный MVP в сложную промышленную платформу без отдельного решения команды.

## 2. Архитектура и границы ответственности

- **Frontend:** PWA на JavaScript. Конкретный фреймворк и структура должны определяться по фактическим файлам проекта; не предполагайте React/Vue и другие технологии без проверки.
- **Backend:** Python + FastAPI.
- **Database:** PostgreSQL в Neon.
- **API-документация:** Swagger UI доступен локально по адресу `http://127.0.0.1:8000/docs` при запущенном backend.
- **Backend MVP уже реализован.** Не переписывайте его и не меняйте API-контракт без конкретной необходимости и согласования с ответственным за backend.

### Важное решение: персональные данные

Backend **не хранит**:
- аккаунты и регистрацию пользователей;
- ФИО, email и телефон пользователей;
- профили доноров;
- личную историю донаций;
- индивидуальные сведения о здоровье.

Личный дневник донаций, выбранные пользователем даты и напоминания относятся к локальной части приложения и должны храниться на устройстве пользователя (для MVP — `localStorage`, если текущая реализация не предусматривает иного).

Не добавляйте отправку этих данных на backend, аналитику или сторонние сервисы без отдельного явного решения команды. Не используйте реальные медицинские данные в демонстрациях и тестах.

### Что хранится на backend

- общедоступные сведения о центрах сдачи крови;
- мероприятия;
- информационные правила/памятки;
- матрица интервалов между типами донаций с датами действия и ссылками на источники.

Матрица включает коды типов:
- `whole_blood`;
- `rbc_1_unit`;
- `rbc_2_units`;
- `plasma`;
- `platelets`;
- `granulocytes`.

Не придумывайте медицинские интервалы и нормативные значения. Используйте данные из backend и их источники. Если значение или трактовка неясны, обозначьте вопрос команде.

## 3. Известный API-контракт

Основные группы маршрутов:

| Группа | Назначение |
|---|---|
| `GET /api/health` | Проверка доступности API и соединения с БД |
| `/api/centers` | Получение списка и отдельного центра; административные операции создания, изменения и удаления |
| `/api/events` | Получение списка и отдельного мероприятия; административные операции создания, изменения и удаления |
| `/api/rules` | Информационные правила и памятки; административное управление |
| `GET /api/donation-intervals/matrix` | Получение матрицы интервалов; поддерживается параметр `for_date` |
| `POST /api/donation-intervals/matrix` | Добавление новой версии матрицы интервалов (административная операция) |

Это обзор групп, а не замена OpenAPI. Перед написанием интеграции проверьте точные пути, query-параметры, обязательность полей, форматы ответов и коды ошибок в Swagger (`/docs`) или в `backend/app/schemas.py` и роутерах. Не додумывайте названия полей.

### Права доступа

- Публичное приложение читает общедоступные данные через GET.
- Запись/изменение/удаление административных данных защищены backend-зависимостью с заголовком `X-Admin-Key`.
- Для MVP администрирование выполняется через Swagger.
- **Нельзя помещать `ADMIN_API_KEY` в JavaScript frontend**, публичный репозиторий, localStorage или сборку PWA. Любой секрет, отправленный в браузер, считается раскрытым.
- CORS не является авторизацией. Не расширяйте CORS и список методов без реальной потребности и согласования.

## 4. База данных и миграции

- Команда использует одну общую базу Neon PostgreSQL.
- Строка подключения `DATABASE_URL` передаётся участникам безопасным способом и хранится только в локальном `backend/.env`.
- Не коммитьте `.env`, пароли, API-ключи и другие секреты. Для примера конфигурации существует `.env.example` с заглушками.
- Alembic-миграции применяет только ответственный за backend/руководитель команды. Остальные участники не запускают `alembic upgrade head` на общей базе без прямого поручения.
- Не редактируйте уже применённые миграции. Для изменения схемы создаётся новая миграция.
- Не выполняйте удаляющие или массово изменяющие операции в общей Neon БД ради тестов.

## 5. Локальный запуск backend

Из каталога `backend`:

```powershell
python -m uvicorn app.main:app --reload
```

Swagger: `http://127.0.0.1:8000/docs`.

Для запуска нужны локальное виртуальное окружение, зависимости из `requirements.txt` и корректный `.env`. Не просите пользователя присылать содержимое `.env` или секреты.

## 6. Правила работы ИИ-помощника

1. Сначала изучите существующую структуру и код. Не создавайте файлы и архитектуру вслепую.
2. Сохраняйте текущий стек и принятые решения. Не добавляйте новые библиотеки, сервисы, Docker, авторизацию пользователей или облачные хранилища без обоснования и согласования.
3. Не меняйте публичный API-контракт без объяснения причины и согласования с backend-разработчиком.
4. Делайте небольшие законченные изменения. Не переписывайте рабочие модули целиком ради стиля.
5. Перед изменениями перечислите, какие файлы собираетесь менять и зачем. После изменений укажите, что именно изменено и как это проверить.
6. Объясняйте новые технологии простым языком: команда, где её выполнить, ожидаемый результат.
7. Не выдумывайте готовность функции, теста или интеграции. Отделяйте проверенное от предположений.
8. Не добавляйте в репозиторий реальные персональные, медицинские или секретные данные.
9. Если требования противоречат существующему коду, сначала покажите конкретное расхождение и предложите минимальный вариант решения.
10. Приоритет — работоспособность и простота MVP, а не преждевременная масштабируемость.
